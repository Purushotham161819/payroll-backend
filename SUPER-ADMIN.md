# PayStream Super Admin setup and operation

The portal extends the existing NestJS backend and Angular frontend. It uses the
existing MongoDB database, login page, signed server sessions, CSRF checks, account
write lock and Argon2id password policy. No new dependency, application or database
is required. Nothing was committed or pushed.

## Before first use

Use Node.js compatible with the existing projects and keep MongoDB running. Keep
the existing backend `.env` private. `SESSION_SECRET` still requires at least 32
random characters; see [LOCAL-DEVELOPMENT.md](LOCAL-DEVELOPMENT.md). The existing
`MONGODB_URI` and `FRONTEND_ORIGIN` continue to apply.

**Local lock recovery completed on 29 October 2026.** The legacy `accounts`
lock created at 19:16:11 UTC was removed only after the operator stopped account
writers and explicitly authorized stopping the one remaining background watcher.
Privileged process inspection verified no writers remained. Exact-owner/timestamp
conditional deletion, unchanged account/business data and index digests, fresh
lock acquisition/release, concurrent-writer rejection, and normal backend startup
were verified. The backend is running and the lock is absent; no real Super Admin
was created. See [ACCOUNT-LOCK-RECOVERY.md](ACCOUNT-LOCK-RECOVERY.md) for the report.

If a future lock blocks account changes, let any active operation finish. For a
verified abandoned lock, follow the existing
[controlled recovery procedure](AUTHENTICATION.md): stop **all** backend instances,
setup/recovery commands and other account writers before removing only the exact
abandoned record. Never delete accounts/business collections or clear a lock merely
because it is old. Automatic expiration and lock bypass remain disabled.

## Create the first Super Admin

1. Open Command Prompt and run:

   ```bat
   cd /d D:\Projects\payroll-backend
   npm.cmd run create-super-admin
   ```

2. Enter your Super Admin email, password and matching confirmation. Password
   input is masked. Use at least 8 characters (maximum 128).
3. Wait for `Super Admin created`. No default credentials are supplied. Passwords
   are hashed, never printed or stored in plaintext. Do not put them in command
   arguments, screenshots or source files.
4. Repeating setup refuses to overwrite an existing Super Admin. Concurrent
   attempts are serialized by the existing MongoDB account lock. The CLI opens
   no HTTP listener and can run without freeing the backend port.

The trusted recovery command is:

```bat
npm.cmd run recover-super-admin
```

Enter the existing Super Admin email and a new password. Recovery preserves the
role and other accounts, activates this account, and invalidates its old sessions.
It cannot create a missing account or silently turn ordinary setup into recovery.
The existing `create-admin` and `recover-admin` commands remain available. The
Super Admin cannot be created or edited through either account-management API.

## Start and sign in

In a backend Command Prompt:

```bat
cd /d D:\Projects\payroll-backend
npm.cmd run start:dev
```

In a second Command Prompt:

```bat
cd /d D:\Projects\payroll-frontend
npm.cmd start
```

Use the existing processes if already running; do not start a second listener on
an occupied port. After deploying changed source, restart your own development
servers so they serve the current application. Open `http://localhost:4200/login`
and use the Super Admin credentials. The login redirects to `/super-admin`.
Ordinary admins/users cannot enter that area, even by calling its APIs directly.
Super Admin credentials cannot access employee, salary, settings or payroll APIs.

For production, retain the existing HTTPS/cookie/proxy/environment configuration:
build the backend with `npm.cmd run build`, then use `npm.cmd run start:prod`.
Build the frontend with `npm.cmd run build` and deploy its existing output as usual.

## Onboard a customer

1. Select **Customers & accounts**, then **Add Customer**.
2. Enter a trimmed organization name and the first administrator's email.
3. Enter and confirm a temporary password. It must have 8–128 characters.
   Organization ID is generated by the backend; it cannot be supplied by a client.
4. Save. The success message shows an ID such as `ORG000001`. IDs are stable,
   unique and never reused; gaps after rejected attempts are normal.
5. Deliver the temporary password privately to the administrator. The application
   does not display it after saving and does not send email invitations.
6. The administrator signs in at the ordinary login page and must choose a
   **different** password before accessing any workspace or user-management API.
   Changing it invalidates the temporary session; sign in again with the new one.
7. A new workspace starts empty. Configure its statutory deduction settings and
   the three mandatory component rates before calculating payroll, just as the
   existing payroll validation requires.

Names are unique ignoring case. Account emails remain globally unique under the
existing email index: one email cannot represent accounts in multiple organizations.
The existing user model has no separate display-name field, so the portal shows
email addresses for login accounts.

## Manage accounts and organization access

Click an organization name. The **Organization details**, **Organization admins**
and **Organization users** sections show only that organization's login accounts.
They never show employee records. Account lists and audit events are paginated.
Use **Add account**, **Edit**, **Activate/Deactivate** or **Reset password** as needed.
The backend protects the last active organization administrator.

For password reset, enter a temporary password and confirmation, then confirm the
selected email and organization in the second dialog. A completed reset invalidates
existing sessions and requires a different password at the next sign-in. Deliver
the temporary password privately. Existing passwords are never recoverable. Super
Admin recovery uses the dedicated CLI, not this interface.

Deactivating an organization immediately blocks sign-in and subsequent requests
and increments all its accounts' session versions. Reactivation permits fresh
sign-ins but does not revive old sessions. No business data is deleted. Account
role, email, password and status changes also invalidate the affected sessions.

Organization administrators use the existing **User Management** screen. Its
queries, target selection, account creation and last-admin checks now enforce the
persisted organization. Changing request bodies, IDs, query strings, headers or
frontend state cannot switch organizations or grant the Super Admin role.

## Backward-compatible database changes and isolation

- `authusers` supports `super_admin` and optional immutable `organizationId` and
  `mustChangePassword`. Existing account hashes, roles, emails and session versions
  are not migrated. Missing ownership retains the original workspace.
- `organizations` stores stable IDs, names, normalized unique names, status and
  timestamps. `platform_counters` allocates IDs atomically under the account lock.
- `platform_audit_events` records the actor ID, action, organization/account IDs
  and timestamp. No passwords, reset tokens, cookies or payroll details are logged.
  Mutations record write intent before changing an existing account and completion
  afterward. If completion reporting fails, inspect the account and audit history
  before retrying; an intent event alone does not claim success.
- Onboarding works on standalone MongoDB: first create a **pending** organization,
  then its administrator and audit events, then activate it. A failed request
  compensates only its own pending records. A process/database outage can leave a
  visible pending organization, which cannot sign in or be activated through the UI.
  Operator review is required: verify its exact organization/account/audit records
  and all writers before repairing or removing only that incomplete onboarding.
  Do not delete any customer or legacy business records. A lost activation
  acknowledgement never causes deletion of an already-active organization's admin.
- Existing `employees`, `employee_counters`, `salary_components` and
  `statutory_deductions` collections stay in place. They are **not assigned or moved**
  to a new customer. Existing single-organization accounts continue using them and
  the `ORGANIZATION_NAME` environment setting. These legacy accounts are managed by
  their existing administrator, not listed as an invented customer in the portal.
- Each new organization uses collections prefixed with its stable ID, for example
  `org000001_employees`. A request-scoped AsyncLocalStorage context is populated
  exclusively from the authenticated database account. Tenant-aware model providers
  select these collections on every business operation, including raw employee
  index access and identifier counters. Unique employee emails and `EMP001` IDs can
  therefore coexist across customers. Original business calculations are unchanged.
- Employee lifecycle/read/write APIs, salary component/formula APIs, statutory
  singleton settings and annual payroll GET/POST paths use these models. Payroll
  reports remain calculated from the current workspace; no payroll-history API or
  separate persisted report store was introduced. Super Admin has no business-data
  route exception.
- Customer header identity reads the current persisted organization's name. The
  legacy header still reads `ORGANIZATION_NAME`. There is no organization switcher
  or customer-controlled ownership field.

This isolates the current application's audited HTTP business APIs. It is not a
separate MongoDB security principal or database per customer. Database operators
retain database access. Future business models, background jobs and direct database
tools must explicitly use the same trusted tenant context/model provider; never
inject an unscoped business model or accept a tenant ID as authorization. Model
caches/collection counts grow with customers; very large deployments need capacity
planning. Converting the original workspace into a named customer is a separate,
explicit migration and was not performed.
