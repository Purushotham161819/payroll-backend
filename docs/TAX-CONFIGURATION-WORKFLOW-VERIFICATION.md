# Tax Configuration workflow — fixes and verification

31 October 2026. Scope: the two reported Tax Configuration issues, confirmed related configuration defects, regression protection and the requested beginner testing guide. Both repositories remain on `main`; no commits or pushes were made.

## Findings and corrections

### Save New Revision and understandable product names

The populated master amounts alone do not make a complete revision. Every salary mapping's approved treatment and legal reference, official source URLs, review note and employer contribution review confirmation remain mandatory. The form correctly rejected missing items, but did not explain the mapping fields properly: its numbered-control parser used `(d+)` rather than a digit pattern, so `reference0`, `reference1` and `reference2` leaked into validation messages.

Read-only inspection of the application's existing `ORG000001` salary collection confirmed the present mapping:

| Old internal control | Product name | Original identity |
| --- | --- | --- |
| reference0 | Basic Salary | 6ae3c1b241976bc8feddb841 |
| reference1 | Dearness Allowance | 6ae3c1b241976bc8feddb842 |
| reference2 | Retaining Allowance | 6ae3c1b241976bc8feddb843 |

This was verified from actual records and source ordering, not assumed. The legacy collection also contains House Rent Allowance, illustrating why another organization may have a different list. No mapping position or product name is hardcoded in the UI.

The parser now recognizes numbered controls, resolves their current component names, and displays messages such as **Legal reference is required for Shift Allowance.** Fields themselves use **[product name] — taxability treatment** and **[product name] — legal reference**, following the user's clarification. Invalid numeric fields, age ranges, slab structure, surcharge structure, missing evidence, missing review and API errors have separate understandable messages. Internal field names are not displayed.

The form now checks the entire configuration before enabling/submitting Save: complete supported master values, contiguous sorted slabs, exactly one unlimited final slab, valid increasing surcharge thresholds, supported age/rounding values, one current mapping per identity, explicit reviewed treatments, required references/conditions and review fields. The backend independently enforces these rules. No tax rate or calculation sequence was changed.

### Load Current Salary Components

The old button invoked `resetMappings()`, which only reused a cached initial list. It did not make a request and rebuilt the mapping array with blank references and a default Fully Taxable treatment. This explains the apparent lack of response and the loss of entered review data.

The new handler calls the existing **GET /salary-components** endpoint, shows a loading state and loaded count, merges by original component identity, retains entered treatment/reference/conditions/partial values and adds newly configured components once. New rows have **Select reviewed treatment** and blank legal evidence; the application does not silently classify them as taxable or exempt.

Active earnings and allowances are eligible. The source endpoint returns all tenant definitions, ordered by creation time and identity. Inactive and employee deduction definitions are not added as new taxable salary rows. Previously entered mappings that become inactive or disappear are retained and flagged. Removing one is an explicit **Remove [name] from this draft** action; saved revisions are not deleted or changed.

Employer EPS/EPF/ESI amounts generated by the existing annual engine are separate annual cells, not fabricated component definitions returned by this endpoint. If an employer-related amount actually exists as an earning/allowance definition, it is loaded under its real name/identity; the separate employer tax-treatment review remains mandatory.

### Additional confirmed defects

1. MongoDB can minimize/omit an empty `published` map when initially creating the registry. Returning that missing map left first-revision History consumers without the object they expect. Registry responses now normalize empty publication/history containers. No customer migration or historical rewrite is required.
2. Activation previously validated only the stored rule structure and could publish a revision whose salary-component set was no longer current. A failing real API test reproduced this. Activation now rechecks the current tenant's active earning/allowance identities and asks the user to refresh/save a new revision if they changed.
3. New saved mapping revisions now snapshot `componentName` from the canonical tenant-owned record. Client-supplied names are not trusted. Future renames/inactivation do not replace the product names in that saved revision. The field is optional for older snapshots; no old revision is rewritten.

## Manual deliverable and remaining limits

The [manual guide](TDS-ENGINE-MANUAL-TESTING-GUIDE.md) contains **123 manual cases** using all eleven requested columns, six required parts, exact setup/field values, valid/invalid configurations, expected messages, eight full salary/slab/relief/cess/annual/monthly/Net calculations, payroll preservation checks and space for the tester's observations. Manual Actual Result/Remarks remain blank and Status is **Not Tested** for the user's environment. Automated results above must not be copied into those manual cells as if the user had performed them.

No remaining Save/Load workflow defect was found in the completed checks. Actual organization-specific statutory review and manual execution in the user's QA environment remain necessary. Only defined QA wage fixtures are given exact reference/treatment inputs; real allowances/benefits still require review. This is not certification of every statutory scenario.

Existing engine limits remain: resident salary-only ordinary income, operative PAN, full-year unchanged monthly allocation, reviewed age band, no supported exemption claims/investment/professional-tax adjustment workflow, previous-employer/opening balances, catch-up reconciliation or confirmed remittance. Unsupported conditional claims still block actual tax calculation. Employer contribution tax treatment must be reviewed separately. The final March 2027 residual case is automated; the existing UI's calendar-year selector does not offer that future month during October 2026.

Annual CTC, Gross Wages, salary formulas/classifications, employer/employee statutory formulas, Net calculation methodology, Run Payroll processing, finalized records/PDFs, authentication and organization isolation were not changed by this task. All pre-existing local work was preserved.
