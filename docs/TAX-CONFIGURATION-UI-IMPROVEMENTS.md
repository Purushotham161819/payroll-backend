# Tax Configuration UI/UX improvements

## Implemented UI

- Removed the full-width separator below the Tax Configuration tabs. Existing navigation and the selected-tab underline/background remain.
- Retained Financial Years as a card, moved Add Financial Year to its top-right header, and reused the existing validated form in an expandable panel.
- Financial Years now uses a responsive table with name/code, start/end dates, status and an activation action with an accessible label and tooltip. The existing confirmation workflow is preserved. No financial-year deletion or unsupported editing API was introduced.
- Tax Master, Progressive Tax Slabs, Surcharge Thresholds and Salary Component Taxability each have a separate card, saved/dirty badge and bottom-right Save button.
- Slabs, surcharge and taxability use structured tables. Existing add/remove controls, unlimited final slab boundary, taxability options, conditional/partial fields, legal references, sources, review notes and employer contribution review fields are retained.
- Actual salary component names, codes and identities come from the existing Payroll Generator service. No components or reviewed values are generated by the UI.
- Tax History is a responsive table showing version, year, regime, effective date, creator, creation date and publication status. The latest revision per year/regime is marked. Pagination uses ten rows per page.
- Existing copy-to-editor and activate actions remain available as labeled icon buttons. View opens a read-only native dialog with the saved rules and reviewed sources. Dialogs support keyboard dismissal and restore focus to their opener.
- Styling follows the existing green Settings theme, with consistent card spacing, table headers, buttons, empty states, scroll regions and focus indicators. The production screen was visually inspected at desktop and 390-pixel mobile widths.

## Card saves and unified versioning

The existing backend accepts only a complete, validated Tax Configuration revision. Its API, MongoDB schema, optimistic registry version, immutable revision history and publishing behavior are unchanged.

A card save starts with the most recent saved revision for the selected financial year/regime, replaces only that card's section and posts one complete snapshot to the existing `POST /settings/tax-configuration/revisions` endpoint. Unrelated fields come from the saved baseline, not from unsaved editor entries. Unsaved changes in other cards remain visible and dirty after persistence. The saved card alone adopts the server's canonical returned values, so normalization does not leave it incorrectly marked dirty.

| Action | Section included from editor |
| --- | --- |
| Save Tax Master | Master amounts, age range, rounding and marginal-relief settings |
| Save Progressive Slabs | Complete slab array only |
| Save Surcharge Thresholds | Complete surcharge threshold array only |
| Save Component Taxability | Component mappings, legal sources, review note and employer contribution review confirmation |

Each save validates the relevant form group and the proposed complete snapshot using the existing configuration validator. Invalid edits in unrelated cards do not block a valid section save. Genuine dependencies still apply: the existing backend must receive a complete valid revision and current component identities. Server validation and version conflicts are shown without discarding any edits.

Only one request can run at a time. The active card shows Saving, writes are disabled during persistence, and duplicate submissions are ignored. Each card has its own success/error message. All saves append to the same revision history; no separate section records, histories or backend endpoints were created.

The first revision cannot be saved partially through the existing API. Until a complete baseline exists, the page explains that all required fields must be completed and saved with the existing **Save new revision** action. That action is also retained for intentionally saving several cards together. Card Save buttons become available once a saved baseline exists and the card contains changes.

Saving does not publish. The existing **Activate revision** action in Tax History, with confirmation and the current registry version, publishes a reviewed revision separately. Saving an unpublished section does not change the currently published rules used by TDS/payroll.

On page reload the latest saved configuration for the initial selected year/regime loads into the editor. Reloading after an API error refreshes state and salary component metadata while retaining current editor entries. Historical copies continue creating new revisions instead of modifying old ones.
